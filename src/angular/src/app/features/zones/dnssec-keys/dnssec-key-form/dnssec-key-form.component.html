Retiring a key removes it from the zone's DNSKEY set immediately and stops it from signing anything, with no transition period -- Ninlil doesn't stagger this automatically. Retire a key only after any resolver that might still hold a cached signature or DS record referencing it has had time to move on (a KSK especially, since a parent zone's DS record has to be updated first); retiring too early can make signed answers fail validation for real clients until those caches expire.

Generating a key here activates it immediately -- it starts signing (ZSK) or gets published in the DNSKEY set (KSK) right away. Ninlil doesn't choreograph a safe rollover for you: a proper rollover (RFC 6781) means publishing the new key alongside the old one, waiting out any relevant TTL/caching window so validators pick it up, and only then retiring the old key -- all of that timing is on you to manage by hand.

A Key Signing Key (KSK) signs the zone's own DNSKEY set and is the key a parent zone's DS record points to -- it anchors the chain of trust, so rolling it means coordinating a new DS record with the parent. A Zone Signing Key (ZSK) signs the zone's day-to-day records and isn't referenced from outside the zone, so it can be rotated more cheaply. Most zones need one of each.

RSA (SHA-1/SHA-256/SHA-512 variants) is the most broadly compatible with older validators but produces the largest signatures and keys. ECDSA P-256/P-384 and EdDSA (Ed25519/Ed448) are modern, widely-supported choices with much smaller signatures and faster signing -- ECDSA P-256 or Ed25519 is a reasonable default for a new zone. MD5 and SHA-1-based algorithms are kept only for compatibility with existing deployments and shouldn't be chosen for a new key.
