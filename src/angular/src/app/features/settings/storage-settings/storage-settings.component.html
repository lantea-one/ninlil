Switches this already-running server onto a different database engine, in place -- no restart, no Docker, no systemd. This backs up the currently active engine, provisions and migrates the target, flips this process onto it, and restores the backup into it. Only the four relational engines below can be switched to or from live; MongoDB still requires editing configuration and restarting.

Every zone, record, key, credential, user, role, API token, filter list, client group, forwarder, webhook subscription, and DNS rewrite this server holds carries across -- this reuses the exact same full backup/restore mechanism as the Backup & Restore page, with the same scope. The persistent query log, the zone-transfer journal, and server logs/metrics are not included either way, for the same reason they're left out of a manual backup: diagnostic history, not configuration this server needs in order to keep working.

The target is connected to and fully migrated before anything about this server's live storage changes -- a wrong host name, an unreachable server, or a rejected username/ password is caught right there, and the switch stops with this server still serving every request from its current engine, completely untouched. Only once the target has proven reachable does the switch back up the current engine and start copying data into it; a problem at that later stage reverts this process back onto the engine that was active before you clicked Switch, whose own data was never touched either. While a switch is running, every other administrative request (including this page's own other tabs) is briefly rejected with a 503 rather than risking a confusing, half-restored answer -- real DNS query resolution keeps running throughout, since it's served from this server's own in-memory zone cache, not read fresh from the database on every query.

Warning: if the target database is reachable and already holds real data -- an existing production database mistaken for a scratch one, for example -- that data is wiped and overwritten with this server's own restored data during this switch, exactly like a manual restore on the Backup & Restore page. Double-check the connection details below actually point at a database you intend to overwrite.

Warning: this switch changes what this already-running process uses in memory only -- it does not rewrite this server's own on-disk configuration to match. If this process is ever restarted after switching (a container restart, a host reboot, a manual stop/start), it comes back up on whichever engine its configuration file's own "Storage" section still names, which -- unless you update that yourself afterward -- is the engine you just switched away from, not this one. Treat a live switch as provisional until the persisted configuration is updated to match; also worth knowing: the previous engine's own data is left exactly as it was, untouched and still switchable back to at any time, but frozen at the moment you switched away from it -- nothing written while running on the new engine appears there automatically.
